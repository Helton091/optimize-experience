# 第二轮跨题跨 case：从 10 道题前三名提炼高手习惯

## 适用场景

第一轮已经详细对照了 SplineConv 的我们与榜首公开实现。第二轮扩大到预赛全部 10 道题，每题当前榜单前三名，目标是寻找**跨算子仍然成立的工程习惯**，而不是继续收集单题技巧。

本轮没有这些题目的本地优化历史，也没有重新编译、上机或做独立收益消融。因此，结论必须比第一轮更克制。

## 证据范围与身份

- 回执：10/10 题、30/30 份前三名记录齐全，包含逐 case 时间与对应提交工作项。
- 公开实现：定位到 26/30 份。它们按队伍和题目分布在官方 monorepo 及 PR 中，不应称为 30 个彼此独立的 Git 仓库。
- 未找到公开源码的 4 份：FalseShare 的 Eigh、answerend42 的 Eigh、LinMingJing 的 SafetyBelt、qunzhongjia 的 SplineConv。仅保留回执，不做源码归因。
- 阅读版本：官方 master `248cf09e…`，SplineConv 榜首公开分支 `f36ce95…`。PR、固定源码和回执链接见[30 份实现证据附录](cross_problem_implementation_matrix.md)。

公开 PR 与队伍名匹配，不代表每个字节都与某次榜单构建相同。ruby0451、北枝等目录还明确区分了**原始获奖归档**与**后续维护拆分版**。本文只评价实际阅读的版本，不把维护版性能冒充原始提交性能。

## 证据等级

| 级别 | 本文含义 | 可以怎么写 |
|---|---|---|
| 代码事实 | 固定版本里确实存在某路径、检查或调度 | “该实现采用/包含……” |
| 跨题复现 | 同类结构出现在不同题目、不同队伍 | “这是常见工程选择，值得作为候选” |
| 回执事实 | 当前榜单与逐 case 时间 | “第一名并非逐点全胜” |
| 机制推断 | 对代码结构为何可能有效的解释 | “下一轮应通过同任务 A/B 验证” |
| 未知 | 未公开源码、未命中路径或未独立复测 | 明确写未知，不补故事 |

同题实现的 token 集合相似度整体不高，未看到近重复提交信号；但这不能证明开发过程独立。因此，“多份实现共同出现”仍只是**工程共识线索**，不是多份独立的性能实验。

## 一、最稳定的跨题习惯

### 1. 快路径按 regime 设计，通用回退按正式实现维护

26 份公开实现普遍存在规模、属性或容量分派，而不是只靠一个循环处理所有输入：

- SwiGLU 三名实现都在小 shape 使用 Vector，大 shape 使用 Cube+Vector，并保留通用计划。
- SplineConv 按 `E/N`、`K/S` 和核权策略选择不同骨架；公开中/大档 `K=9` 时，不能误套 `[2,2]` 专用路径。
- TreeLine 把极小标量、短表、点线块和大规模空间筛选分开。
- Det/Lstsq/Pinv/Solve 普遍区分小矩阵片上驻留、较大矩阵协同分解和通用求解。

**可迁移习惯**：先定义通用正确实现，再用明确的语义条件、容量条件和成本条件增加快路径。通用回退需要同样的正确性测试，不是异常时才想到的附属品。

**不能推出**：具体阈值、shape 表或编译变体越多越好。大量常量只说明工程覆盖，不说明隐藏用例收益。

### 2. 先减少有效工作，再谈向量化

高分实现并不是一律“全量读入后用更宽指令”：

- SafetyBelt 的 FP16 路径只转换 `y1/y2/cy` 三列，而不是整个人员框。
- SplineConv 大档按边取 4 个相关核权，避免每核全量预载 9 个。
- TreeLine 小输入直接算，大输入才考虑空间排序和保守筛选。
- Fire 的小路径有溢出检查和修复，其他任务按 owner、帧或批次减少重复先验与地址工作。

**可迁移习惯**：把“哪些字段、边、候选和矩阵真正参与输出”写在 kernel 设计之前，并把筛选/建表成本计入净收益。详见[先做有效工作量选择，再决定向量化方式](../../optimizations/selective_work_before_vectorization.md)。

### 3. 缓存策略由复用率决定，不以“全量常驻”为目标

不同算子的正确选择可能相反：

- SwiGLU 的大路径把两路权重和输入组织成 Cube 流水，通过常驻与双缓冲提高复用。
- SplineConv 大档却选择按边局部核权，因为 `E×S` 比 `执行核数×K` 更小。
- TreeLine 对短表直接复用线段不变量，大输入才投入空间索引。
- Eigh 的 Householder 反变换保存并复用反射子信息，而非每轮重建所有中间量。

**可迁移习惯**：比较全量缓存、按需加载和共享复用时，同时计算工作集、复用次数、UB 容量、DMA 描述符和首次等待。不要为了“缓存率”引入超过工作本身的预取。

### 4. 先设计数据所有权，再决定核数与同步

常见分工不是简单“核越多越好”，而是：

- 独立 batch、点、帧或节点优先分配给不同核，减少全局同步。
- SplineConv 用 edge/node owner 和清零角色避免原子累加。
- 大矩阵才组成小组，在 panel、列或块上协作，并配套 workspace、主元与同步协议。
- SplineConv 中档的 48 核与大档的 8 核说明核数必须随骨架重新求解。

**可迁移习惯**：先写出“谁拥有这份输入/输出、是否有人重复读写、最慢核做什么”，再选择核数、workspace 和 flag。独立任务优先，协作只在单任务规模或算法依赖需要时引入。

### 5. 数值快速路径配有分级回退

这是 Det、Lstsq、Pinv、Solve、Fire 和 TreeLine 中最有共性的数值工程习惯：

1. 保留快速主路径；
2. 用真实主元、残差、范数、上溢或平局条件做检查；
3. 能局部修复就做残差修正、补偿或迭代精化；
4. 必要时进入部分主元、QR、Jacobi、精确有理数等稳健完整路径。

但反例同样重要：

- Solve 三名实现主要是主元和残差修正，未见统一的失败后换算法。
- Det#2 未见失败后重算回退。
- 某些“回退”只覆盖特定快速路径，不能概括整个实现。

**可迁移习惯**：为每级记录触发条件、输出语义和最大额外成本，并用独立负对照触发。详见[给快速数值路径设计分级回退](../../optimizations/numerical_fallback_ladder.md)。

### 6. 不变量放在 Host/编译期，热路径避免通用脚手架

公开实现反复出现以下组织：

- Host 计算分块、布局、主元/倒数乘子和容量计划；
- 用编译期 key 选择资源，压缩必要的元数据；
- 使用静态 UB 偏移或轻量 arena，减少通用队列与字段物化；
- 对地址、索引和掩码预生成或复用，而不是每条数据重新准备。

TreeLine 的压缩描述符、Fire 的地址表、Det 的静态偏移、SplineConv 的最小单边入口属于同一类工程思想。

**可迁移习惯**：区分“输入相关数据”和“执行计划”。计划尽量在 Host/编译期确定，热路径只消费必要字段。

**不能推出**：任何 tiling 读取或 `TPipe` 都一定昂贵。第一轮已经证明，少读字段与完全绕过通用入口不是同一层级的优化。

### 7. Cube、AIV、底层 intrinsic 都是结构选择，不是身份标签

跨题没有统一的“高分就必须 Cube”规律：

- SwiGLU 大 shape、部分 Det/Lstsq/Pinv 使用 Cube 或 AIC/AIV 协同。
- TreeLine、Fire、SplineConv 的大量热路径完全依赖 AIV。
- Eigh 主体是 AIV，大矩阵反变换才使用 MIX/Cube。
- Solve 的若干实现即使声明 MIX_AIV，也未核实实际 AIC/Matmul 计算。

同样，使用底层 `vgather/vbrcb/vcmp` 不自动优于 `Gather/Brcb/Add` 等高级 API。底层写法只有在布局、repeat、mask 和同步都得到验证后才有意义。

**可迁移习惯**：先完成数据流与工作量优化，再按端到端总账选计算单元和 API。声明 MIX 不等于使用了 Cube，必须读实际执行路径。

### 8. 逐 case 组合比“单点神技巧”更重要

当前回执显示第一名并不逐点全胜：

| 题目 | 回执中的反例 |
|---|---|
| TreeLine | 第一名在某大 case 为 964.12µs，第二名为 603.38µs |
| Solve | 第二名在某 case 为 82.66µs，优于第一名的 94.54µs |
| Eigh | 第一名与第二名在已有点上各有 6 个逐 case 最优 |
| SwiGLU | 三个名次都拿到过逐 case 最优，第一名并非全面碾压 |

**可迁移习惯**：保留逐 case 的优缺点，不用总分反推每条路径。优化时应同时看最弱 case、其他 case 是否回退，以及不同路径之间的组合，而不是只追求某一个公开点。

### 9. 版本溯源和复杂度预算本身就是工程能力

ruby0451 的 Det/Solve 与北枝的 Pinv 明确记录：哪个归档版本对应正式提交，当前维护版做了哪些拆分/修复，哪些结论尚未重新上机验证。这比“代码在 main 上，所以比赛成绩也证明 main”严谨得多。

同时，SwiGLU、TreeLine 等题目中，第一名实现的文件/代码量并不总是最大。模板、布尔开关和底层 intrinsic 的数量不能作为性能证据。

**可迁移习惯**：给每份结论绑定源码 commit、回执、维护状态、阅读范围和未验证项。复杂代码只有在能解释成本、测试和维护收益时才值得保留。

## 二、不能从 30 份回执推出什么

| 看似合理的推断 | 为什么不能直接下结论 |
|---|---|
| 所有第一名都有公开的逐字获奖代码 | 4 份源码未找到，另有维护版与原始归档差异 |
| 第一名在每个 case 都最好 | 多题出现第二、第三名逐点更快 |
| 全量缓存一定优于按需加载 | SplineConv 大档恰好相反，需比较复用与矩阵数 |
| 核越多越好 | 不同骨架下出现 8 核与 48 核的各自合理选择 |
| Cube/底层指令一定优于 AIV/高级 API | 多个高分实现主体完全使用 AIV |
| 模板越多、代码越复杂越快 | 代码规模与名次没有稳定关系 |
| 公开 shape 的常量可直接复用到隐藏 case | 常量只证明公开工程覆盖，隐藏分布未知 |
| 多份实现重复出现就等于独立实验证明 | 无法排除共同模板、相似实验条件或相互借鉴 |

## 三、把这些习惯用于新算子的顺序

1. **建立通用基线**：先保证全部合法输入正确，保留可独立调用的通用路径。
2. **画 regime 表**：记录 shape、属性、入度/稀疏度、工作集、UB 和合法回退，而不是只列公开 case。
3. **先删工作**：检查字段、候选、核权、空输出和无效任务能否减少，并扣除选择成本。
4. **再定复用与所有权**：选择全量缓存/按需加载、独立任务/协作小组、核数和同步。
5. **压缩执行计划**：把不变量移到 Host/编译期，避免热路径携带无用通用状态。
6. **选择计算单元和 API**：以完整调用总账决定 AIV/Cube、底层/高级接口。
7. **加入数值分级回退**：明确 L0 快路径、L1 检查、L2 修复和 L3 稳健算法。
8. **逐 case 验收**：记录每个 case 的正确性、时间、回退、寄存器/UB 和最慢核，防止一个点的收益掩盖其他点回退。
9. **保留证据身份**：commit、回执、维护差异、测试范围和未知项一起保存。

只有完成同任务、同精度、同窗口 A/B 后，才能把其中的候选习惯写成“本算子采用”。

## 四、证据强弱总结

**可以作为高优先级工程候选**：regime 分派、通用回退、有效工作量选择、按复用率缓存、明确所有权、数值分级回退、逐 case 验收。

**只能按题目重新求解**：核数、缓存大小、tile、具体 API、是否使用 Cube、补偿次数、调度模式。

**不能直接继承**：公开 shape 常量、UB 魔术偏移、模板数量、名次对应的独立模块收益、未公开实现的所谓技巧。

完整逐题逐队证据见[30 份实现证据附录](cross_problem_implementation_matrix.md)。

## 失效边界

- 本轮是公开源码与回执的静态复盘，不是独立性能实验。
- 源码未公开、维护版差异、未命中路径和未触发回退均已保留为未知。
- 不把不同算子的绝对时间横向比较，也不把公开 case 的分布推广到隐藏 case。
- 任何“高手习惯”都只是下一轮设计候选，不是免验证的优化公式。
